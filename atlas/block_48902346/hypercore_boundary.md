# HyperCore boundary in saved Papertrade executions

The [call ledger](hypercore_boundary_behavior.json) decodes 482 HyperCore boundary calls in 170 distinct saved transaction traces: 139 have paired receipts, and 31 additional stratified withdrawal traces have callTracer logs. A boundary call appears in 110 of those transactions. The counts describe this saved corpus, not all Papertrade history.

| Target | Saved calls | Calling path | Checked result |
|---|---:|---|---|
| `0x0801` spot balance | 131 | Exchange signed/direct withdrawal and sweep request/finalization | Two input words, three output words, token 0 in every saved call |
| `0x0803` withdrawable | 26 | Exchange sweep request/finalization | One address input and one output word; all 26 outputs are zero |
| `0x080e` best bid and offer | 102 | Oracle midpoint getter | Two positive price words; 57 instrument-0 and 45 instrument-1 reads |
| `0x0810` `coreUserExists(address)` | 105 | 103 signed and 2 direct Exchange withdrawals | One address input and a boolean result; 44 false and 61 true |
| `0x3333...3333` CoreWriter | 118 | 105 Exchange withdrawals and 13 user deposit proxy sweeps | All use `sendRawAction(bytes)` with version 1, action 6, token 0 |

Every one of the 102 saved Oracle `0xc0182669` calls returns `floor((bid + ask) / 2)` from its nested `0x080e` response. These calls span 61 transactions and 37 distinct instrument/price pairs. This extends the earlier 20-call midpoint check without claiming that every possible BBO input was exercised.

All 118 CoreWriter actions decode as spot sends. For 105 Exchange calls, the destination is a user address; for 13 user proxy calls, the destination is Exchange. The encoded amount is a positive `uint64` in eight-decimal Core units. Every one of the 19 writer calls in the paired trace corpus has a matching canonical receipt log. The remaining 99 have a matching callTracer log but no saved receipt in this corpus. No historical action 7 occurs in these saved traces; the user proxy's action 7 branch is covered by a separate exact-runtime local replay.

The [signed withdrawal corpus](exchange_withdrawal_trace_corpus.json) links all 103 saved signed calls to exactly one `0x0810` read, one `0x0801` read, one CoreWriter spot send, and one canonical `CoreWithdrawal` event in the complete event history. The writer destination is the signed user and its amount is the six-decimal signed raw amount times 100. All 43 false `coreUserExists` results have exactly one extra internal USD debit; all 60 true results have no extra debit. Four calls have saved receipts and 99 have callTracer event logs matched to the complete on-chain log history. Two separately saved direct withdrawals show the same split. The full 28,643-event history has only these two debit patterns, but user-existence results are not known for every event.

[Hyperliquid's CoreWriter documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/hyperevm/interacting-with-hypercore) defines action 6 as a spot send and explains that a CoreWriter EVM log queues an action for later HyperCore processing. The [independent first-party `0x0810` source](hypercore_user_exists_evidence.json) names the account-existence read. These sources describe the boundary protocol, not Papertrade's Solidity source. A separate [public HyperCore ledger capture](../../artifacts/audit_sweep_settlement/public_ledger.json), checked by [`audit_sweep_settlement.py`](../../scripts/audit_sweep_settlement.py), matches all 13 sampled proxy-to-Exchange spot sends to Core transfers of the exact credited amount before EVM finalization. This is independent API evidence of delivery for that sample; the saved EVM calls alone do not prove delivery. A second [public Core ledger capture](../../artifacts/audit_withdrawal_settlement/public_ledger.json), checked by [`audit_withdrawal_settlement.py`](../../scripts/audit_withdrawal_settlement.py), matches two direct and two signed Exchange withdrawals to transfers visible on both sender and recipient ledgers. The two new-account cases record a one-USDC fee, equal to the extra EVM debit; the two existing-account cases record zero fee. Full-history delivery and the ultimate fee recipient remain open.
