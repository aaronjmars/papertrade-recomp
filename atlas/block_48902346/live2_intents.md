# Signed intents, execution gates, and the deposit and withdrawal paths on the post-pin suite

This is the readable companion to [`live2_intents.json`](live2_intents.json), generated by
[`audit_live2_intents.py`](../../scripts/audit_live2_intents.py). It covers the fifth audit angle: signed
intents (EIP-712 and nonce edges, session-key lifecycle), the execution gates that admit them
(BatchExecutor allowlist, the Exchange caller slots), the withdrawal debit rule, and the deposit and
sweep paths as a liveness and authorization surface.

Two runtimes are compared everywhere: the pinned contract set 1 and the live **contract set 2** the
2026-10-21 six-call governance batch installed behind the same proxies. Every claim names which
runtime it applies to. Nothing here is an advisory or a disclosure; no transaction, upgrade or
governance action was performed.

## Method and evidence tiers

1. `audit_live2_intents.py` compiles one Foundry harness twice: once against the pinned
   implementations (the control) and once against the set 2 implementations (the live
   configuration). Both use a port-free local EVM, the exact captured runtimes, the saved pinned
   Exchange storage words, the recorded HyperCore read responses supplied as mocks, and a recording
   CoreWriter. HyperCore reads are **mocked** in every case; a mocked read is never a live
   observation.
2. A third pair of runs compiles only the differential cases against each runtime set, so the two
   implementations answer the same question in the same harness.
3. Head-era facts come from **saved** read-only captures under `artifacts/` (no RPC credential is
   used offline): `artifacts/postpin_pin/raw_reads.json` at head 49,260,476 and
   `artifacts/postpin_suite/live_latest.json.gz` at head 49,255,838.
4. The pinned side of the sweep differential is cross-checked against the saved archive-fork case
   corpus in `artifacts/exchange_sweep_archive_local/`, which reproduces on the pinned code exactly
   (see below), so the local construction is calibrated rather than asserted.

Results are pinned in `artifacts/live2_intents/forge_observations.json`; every observation is a
pinned integer or boolean and the harness fails if any of them moves. Every error selector and event
topic this ledger *names* is hash-checked in the script against its signature, and the selectors it
leaves unnamed are listed explicitly in the ledger's `verified_names` block rather than given a
plausible-looking label.

## D1 Signed intents, domain separation and nonce edges

The EIP-712 domain is `keccak256(abi.encode(EIP712Domain typehash, keccak256(name),
keccak256(version), 999, authorizedCaller))`, where `authorizedCaller` is stored in
SessionKeyManager slot 3 and equals the **Exchange proxy** address. `DOMAIN_SEPARATOR()` returns the
initialization-time cached word in slot 1 while `domainSeparatorV4()` recomputes it, and the
verification path uses the recomputed value. At the pin both are
`0x53a2ab5a64b3239d36b108fb4cd035ebb40ed3f71dec28e37966622670147e77`.

A live head read at block 49,263,577 confirms that this is unchanged on the running set 2 code:
SessionKeyManager slot 1 holds that separator, slot 3 still holds the Exchange proxy,
`DOMAIN_SEPARATOR()` and `domainSeparatorV4()` both return it, and slot 8 holds
`0xfdc6550436dd75ce8a0b145f935b7d3a64f53248` (the BuilderRegistry).

| Check | Result | Runtime |
|---|---|---|
| A withdrawal signature built for the pinned domain (slot 1 word and constant) | accepted by the set 2 SessionKeyManager and Exchange; the nonce bit and counter persist | set 2 |
| The same signature with any changed field, or a one-bit-different domain | rejected `0xc20280ea`; the nonce bit and counter roll back and the CoreWriter is untouched | set 2 (and pinned, identical) |
| A registration digest signed by the session key instead of the user | rejected `0x8baa579f` (`InvalidSignature`), so a compromised session key cannot register further keys, and no extra nonce bit is marked | both |
| Nonce bit already consumed by a different intent class | open, close, withdrawal and registration all reject `0x756688fe` (`InvalidNonce`) | set 2 |
| Same bit index in the next bitmap word (`nonce + 256`) | accepted, and the bit persists in the second word only | set 2 |
| Same nonce for a different user | reaches the signature check, so the bitmap is per user | set 2 |
| Deadline one second before the block timestamp / equal to it | `0xf87d9271` (`ExpiredDeadline`) with the bit unused / reaches the signature check for all three intents | both |
| Session key expiry one second past / exactly at the block timestamp | rejected `0xc5045f22` / **accepted** (the boundary is inclusive) | set 2 |
| Session key word with a non-zero associated address | accepted when signed by the registered key; rejected `0xc5045f22` when signed by the associated address, so the field is metadata rather than a signer | set 2 |
| `revokeSessionKey` then a signed close | the word is cleared and the close rejects `0xc5045f22` | set 2 |
| Validly signed open on the set 2 runtime | still reverts with the unresolved `0x0a4f5a07` after the signer check, exactly as pinned; recorded, not asserted | set 2 |

Reading against the pinned evidence: the pinned encryption of a nonce into a shared bitmap word is
unchanged in kind, but **the class boundary is only the typehash**. Any class can consume a nonce
bit that another class would use, which is by design (a single nonce stream per user) and reachable
only through the Exchange or the authorized submitter, so it is not a finding.

## The set 2 builder fee: is the builder bound, and who can claim it?

The contract set 2 Exchange adds `claimBuilderFees()` (`0x69f9a5f0`), `builderFees(address)`
(`0x9d346583`) and a builder accumulator at slot 39 with a shared slot-38 counter. Two mechanistic
questions were put to this workstream by the authority angle; both are answered on the exact runtime.

| Question | Result |
|---|---|
| Does the signed close bind the builder field? | The signature covers exactly the pinned five-field struct: the live `CLOSE_TYPEHASH` (`0x9cc23a52…`) is byte-identical to the pinned constant, which hash-verifies to `Close(address user,uint256[] positionIds,uint256 nonce,uint64 deadline)`, the close selector stays `0x2792e706` with seven arguments, and a locally generated signature over that struct is accepted. So a builder address is **not** a signed field. |
| Can a relayer steer the fee through extra calldata? | No evidence: appending an unsigned eighth word keeps the signature valid and the close still succeeds, but it changes neither the credited accumulator key nor the write set, and a six-element `positionIds` array does not turn any element into the credit key. |
| Then where does the credited address come from? | Unresolved. The credit site keys on `mload(args_base + 0x180)` masked to 160 bits and adds the fee returned by the linked library, and it is only entered when a fee exists: an empty or loss-free close reads 11 Exchange slots and writes none. Naming the source word needs a fee-paying close traced on set 2 (`L2-D1-06`, `plausible_unproven`). |
| Is `claimBuilderFees` per-caller or shared? | Caller-scoped, exact runtime: with accruals of 5e18 for builder A and 7e18 for builder B, A's call pays exactly 5e18 and zeroes only A's entry, B's entry survives, B's call pays exactly 7e18, and the shared slot-38 counter falls only by 5 + 7. An arbitrary address with no entry succeeds and is paid zero. The claim body keys on `keccak256(abi.encode(msg.sender, 39))`. No cross-builder theft (`L2-D2-04`, `disproved`). |
| What does the owner-only `0xd970fad5` do to slot 39? | It moves an accrual between addresses: as the owner, `0xd970fad5(a, b)` zeroes `builderFees[a]` (5e18) and adds exactly that amount to `builderFees[b]` (7e18 becomes 12e18), leaving the shared slot-38 counter untouched; an unrelated caller reverts `0x30cd7471`. |
| Do the sweep-family entries touch the accumulator? | No. `sweep(address)`, `requestSweep(address)` and `finalizeSweep(address)` all succeed in this construction and read or write none of the seeded `builderFees` entries, so the slot-39 block is not on the sweep path. |

## The new per-close verifier and the coupling it creates

The set 2 SessionKeyManager's third added selector, `0xd95208cd`, is not a passive getter: it is the
verifier the set 2 Exchange calls on every signed close. My own trace of a passing close
(`artifacts/live2_intents/close_verifier_calltrace.txt`, produced with
`forge test -vvvv --match-test testSet2CloseBuilderWordIsNotSigned`) shows
`0x6cd56616::2792e706` calling `0x8326eb88::b002b9fa(user, nonce, deadline)` first and then
`0x8326eb88::d95208cd(user, digest, v, r, s)` as a `staticcall` into `0x04b5ea4c`, i.e. the digest is
computed by the Exchange and handed to the SessionKeyManager with `v, r, s`. A direct call with a
digest signed by the user's own key returns `SessionKeyNotAuthorized()` (`0xc5045f22`), so it is a
session-key verifier over a digest. The dispatch bytes `63d95208cd` appear exactly once in the set 2
runtime and zero times in the pinned runtime, and `audit_live2_intents.py` asserts that.

Consequence: the two proxies are coupled, and a deployment that pairs the set 2 Exchange with the
pinned SessionKeyManager keeps taking deposits and withdrawals while **closing nothing**. The failure
mode was settled by AuditAuthority's four-arm negative control (`L2A-15`,
`artifacts/live2_authority/close_coupling.json`): a direct close with the pinned SessionKeyManager
reverts with empty data and writes no Exchange slots, the same close with the set 2 implementation
succeeds with 12 writes, and the historical BatchExecutor batch *succeeds* in both pairings while
writing 4 slots and leaving both positions active under the pinned implementation (22 writes and no
position active under the set 2 one). The batch wrapper is what makes it silent: the inner close
fails, the outer transaction still reports success. My own implementation-swap arm disagreed and was
unstable between runs, so it is retired rather than cited; the two facts I contribute are the call
trace and the dispatch-byte check. This is a live coordination fact for the recovery plan: a
candidate that mixes implementations must not leave this pair mismatched (`L2-D1-07`).

## D3 The withdrawal debit rule

`withdrawToCoreBySig` reads the destination's HyperCore account status at precompile `0x0810`
inside the call and adds one USD to the internal debit when the status is false. Measured on the
live runtime for a signed amount of 2.00 USD (raw `2_000_000`):

| Status read | Internal debit (18 decimals) | Core payload (8 decimals) | Caller |
|---|---:|---:|---|
| false (new account) | `3e18` | `200000000` | BatchExecutor or an unrelated outsider relayer, identical |
| true (existing account) | `2e18` | `200000000` | BatchExecutor |

The extra unit is **not** part of the Core send: the payload stays exactly the signed amount times
100. The pinned event census over all 28,643 `CoreWithdrawal` events shows only two gap classes,
22,652 events debiting the sent amount and 5,991 debiting exactly one USD more, and the 32-case
stratified public-ledger check pairs every status-0 event with a one USD fee entry on the
Exchange's own Core account while the recipient receives the signed amount. So the extra debit funds
HyperCore's new-account spot fee and is a documented pass-through, not an uncompensated user loss
(`L2-D3-03`, status `disproved`). The status value itself is Core-owned: the Exchange reads it fresh
with only the user address as input and holds no cache, so no EVM actor can force either direction.
An observation-only guard found on the way: the withdrawal path admits **one withdrawal per user per
block** and a second call in the same block reverts `0x4f57ffae`, the same guard the pinned
direct-path probe records.

## D4 The deposit path as an attack surface

The deposit proxy's callable surface is four selectors: `user()`, `exchange()`,
`sweepAllToExchange(uint64,uint64,uint64)` (exchange-only) and `withdrawStuckToken(address,uint256)`
(user-only). It has no fallback and no receive function, so a native-value call or an unknown
selector reverts: **there is no EVM funding path into a proxy**. On Core, a proxy can receive funds
from anyone, because Core spot sends are permissionless.

| Adversarial question | Answer |
|---|---|
| Can an outsider drive a victim's sweep? | Yes. `requestSweep`/`sweep`/`finalizeSweep` are permissionless: a caller distinct from the CoreWriter address succeeds, writes the pending word and makes the proxy queue a CoreWriter action 6 for **the entire observed balance** (`queued_total == observed == 1e10` in the test). This is also how PT-01's 5,799 retries happened. |
| Can an outsider push a victim into the wedged state? | No path was found. The request recomputes the amount as the full current balance every time, so a Core-side top-up cannot create a gas reserve; it can only raise the amount queued. The wedge is the Core-side transfer-gas predicate, not an EVM-reachable state. |
| Can a third party influence delivery at all? | Only positively: a top-up that lands between the EVM balance read and the Core execution would supply the missing fee for a doomed send. Untested, and it needs the Core fee rule. |
| What are the request bounds? | `spotRaw + 100 × perpRaw ≥ 1,000,000,000` (10 USDC): `999,999,999` reverts `0x329c2b0f` (`SweepBelowMinimum`), the minimum succeeds. |
| Can the stuck-token rescue be aimed at anything of value? | Only by the user, and only at EVM tokens the proxy happens to hold. A rescue of a no-code address still emits `StuckTokenWithdrawn`, but nothing moves; the venue's assets are Core-side, where this function cannot reach. |
| Are the newest factory proxies identical? | Yes. The CREATE2 derivation reproduces the two saved live stalled-proxy runtimes byte for byte (`405e5bfee919…`, `07f9f589f271…`) and five catalog user→proxy addresses exactly, so the wedge class is family-wide and has no per-user variation beyond the two embedded user words and the exchange word. |

### The retry path changed in set 2 (differential)

The same harness case against both runtimes: pending word `(10,000,000,000 raw, 0 perp, block − 1)`,
mocked current Spot balance `10,000,000,000`.

| Case | Pinned (set 1) | Live (set 2) | Saved archive-fork cross-check (pinned) |
|---|---|---|---|
| Retry above the minimum | rewrites the pending word with the **full** observed balance and queues `10,000,000,000` | rewrites it with `9,900,000,000` (observed − 1 USDC) and queues `9,900,000,000` | `finalize_unchanged_above_minimum.diff.json` stores the full balance |
| Retry at a dust balance (`100,000,000`, below the minimum) | reverts `0x329c2b0f` (`SweepBelowMinimum`), word unchanged | succeeds, clears the pending word, and does not call the proxy | `finalize_unchanged.call.json` reverts `0x329c2b0f` |

This is the same one-USD-reserve shape the two historically recovered older proxies used to get
their Core send executed. It follows that a permissionless retry under the live code asks the proxy
for `balance − 1 USD`, which is the amount that leaves a reserve for the transfer fee, so a stalled
deposit may now be escapable by calling `sweep(user)`. Two caveats, both recorded: the user would be
credited one USD less than the balance observed at the request, the reserved unit would stay in the
proxy's Core account, and whether HyperCore accepts the reduced send for these two accounts is
untested. No sweep request, clear or credit event occurred after the upgrade, so nothing has
exercised this path yet.

## D5 Sibling paths: guards, unprivileged effect, and credit without delivery

| Path | Guard | What an unprivileged caller can affect | Credits without a Core delivery? |
|---|---|---|---|
| Proxy `sweepAllToExchange` | `msg.sender == exchange` (immutable) | nothing; reverts otherwise | n/a |
| Proxy `withdrawStuckToken` | `msg.sender == user` (immutable), non-zero amount, token call must not return false | nothing | n/a |
| Proxy `user()` / `exchange()` | none (read-only) | nothing | n/a |
| Factory (12 selectors) | owner or admin initializers; `proxyOf` is a pure CREATE2 computation | nothing; a user proxy address is derivable by anyone | n/a |
| Exchange `requestSweep` / `sweep` | per-proxy per-block guard, 10 USDC minimum | can re-request or retry any user's sweep; cannot change the destination or the amount | no: finalization credits only when the proxy's Core balance falls |
| Exchange `finalizeSweep` | pending request, request block strictly before the current block | can push any user's finalization, including a retry | **yes, in amount**: see below |
| Exchange `reconcileSweepCredit` | owner only, and rejects an existing pending word (`0x28ef4314`, `NotOwner` `0x30cd7471`) | nothing | it is a credit, but it cannot run while a pending word exists |
| Exchange `clearPendingSweep` | absent from both implementations (empty returndata) | nothing | n/a |

**The finalize credit is delivery-blind.** With a stored snapshot of `100,000,000` raw (1 USDC) and a
mocked current balance of either `1` or `50,000,000`, `finalizeSweep` credits exactly
`100,000,000 × 10^10 = 1e18` in both cases, i.e. the full stored snapshot regardless of how much of
the balance actually left the proxy; treasury, the packed total-balance word and the user balance
each move by that amount. The saved fork corpus shows the same on the pinned code: a one-raw-unit
decrease credits the full snapshot. Controls: an unchanged balance above the minimum and an
increased balance credit nothing (the request is replaced), no pending request reverts `0x0984a617`
(`NoPendingSweep()`), and a same-block call reverts the unnamed `0xd26ffacb`.

Consequence: a proxy balance decrease without an equal Exchange receipt could create a
shortfall, because finalization follows the stored snapshot. No real partial delivery or such
non-delivery balance decrease has been observed. Two older reduced retries paid a separate 1 USDC
sender fee while delivering and crediting exactly the same amount; that fee alone does not prove
overcredit. All 84 recorded newest-set sends to the Exchange had a zero fee.

**The named owner recovery calls are unavailable for the two stalled deposits.** The owner
reconciliation call rejects either pending word with `0x28ef4314`, an unrelated caller gets
`0x30cd7471`, and `clearPendingSweep` (`0x2362f4de`) is absent. The set-2 retry now reserves
1 USDC, but Core delivery and user credit for these two accounts have not been observed.

## Ledger

Twenty-two rows in [`live2_intents.json`](live2_intents.json) in the shared schema, each naming the
runtime it applies to: 1 `confirmed_live`, 16 `confirmed_simulation`, 2 `plausible_unproven`,
2 `disproved`, 1 `blocked`. The strongest rows are `L2-D4-02` (the retry-reserve change, an
exact-runtime differential on both runtimes with a saved-fork cross-check) and `L2-D5-01` (the
delivery-blind credit it makes reachable), with `L2-D5-02` recording that no owner route recovers a
stalled pending word, `L2-D1-06` carrying the open builder-binding question, and `L2-D2-04` and
`L2-D2-05` settling the builder claim as caller-scoped and the owner entry as an accrual
reassignment, and `L2-D1-04`/`L2-D1-07` identifying the new per-close verifier and the proxy coupling
it creates.

## Limits and unknowns

- HyperCore replies are mocked in every local case; the account-status and spot/perp balance reads
  are inputs, not observations. The factory read used by the sweep tests is a mock returning the
  exact CREATE2-derived address, because the recorded factory runtime needs its storage to compute
  `proxyOf`; the derivation itself is checked against five catalog pairs.
- The 13 live-only cases use a constructed prestate: pinned Exchange storage words plus overrides.
  The pinned control suite and the saved fork corpus are what calibrate that construction.
- The fresh head reads were staged and now exist: `artifacts/live2_intents/live_reads.json` holds
  head 49,263,577, both proxy codes, SessionKeyManager slots 1, 2, 3 and 8, the three session getters
  and Exchange slot 88. The post-upgrade `eth_getLogs` census for the `CoreWithdrawal` and
  `SweepRequested` topics is still missing: the endpoint answered `-32005 rate limited` for a long
  stretch and the log queries timed out once it recovered (`L2-D4-03`). Earlier rows therefore also
  cite the saved captures in `artifacts/postpin_pin/raw_reads.json` (head 49,260,476) and
  `artifacts/postpin_suite/live_latest.json.gz` (head 49,255,838).
- Selector `0xd95208cd` in the set 2 SessionKeyManager has no saved call, no public name and no
  allowlisted route; its behaviour remains unestablished rather than guessed.
- The open path's post-signer error `0x0a4f5a07` persists unchanged on set 2 and its source name is
  still unresolved.

## Reproduce

```sh
python3 scripts/audit_live2_intents.py            # offline: hashes, saved reads, control, live and differential suites
python3 scripts/audit_live2_intents.py --capture  # refresh artifacts/live2_intents/live_reads.json from the public endpoint
```

The offline path needs Python 3, `forge` and `solc` and no RPC credential; it fails if any pinned
observation, test name or runtime hash moves.
