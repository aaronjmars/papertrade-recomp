## Pause-clearing sweep on contract set 2

Zero of the 3255 calls cleared the seeded flag and zero changed the seeded word. The only selector that writes a pause-shaped word is `0x2d2451d1` itself, from the owner and the pause guardian, which is the sweep's positive control that a mapping-35 write is detectable at all; the static analysis agrees, with exactly one verified mapping-35 write in each runtime (pinned SSTORE 12354 inside the 12188 pauseMarket body, set 2 SSTORE 11526 inside 11360) and four mapping-35 key-derivation sites in each. The static `sstore_hint` field is deliberately unverified: the pinned hint at 2645 is the mapping-36 side-exposure write inside the signed-open body, not a pause write.

Coverage limit of the sweep: it watches the pause words of instrument ids 0, 1 and 2 (the pinned instrument count is 2) and five argument templates, so a hypothetical path that needs an argument outside those templates is not covered; the static accessor census is the second, independent check, and it finds no other mapping-35 write site to reach. The two methods agree, and no saved evidence contradicts either.

The global trading pause in slot 29 is the reversible control: `setTradingPaused(true)` succeeds from the owner and the pause guardian (`0xae69b95b`) and from nobody else, and clearing it succeeds from the owner only, with the pause guardian getting `0x49199fb6` NotPauseAuthority(). A market-level pause has no such switch in the deployed implementation; a governance upgrade can still rewrite proxy storage, which is the upgrade caveat recorded on LP-02.

## Method and limits

- Static reads are byte scans of the exact runtime files: PUSH4 immediates for the call-site map, a linear opcode census that skips PUSH data, and the dispatcher EQ pattern for the selector sets. The Oracle's zero TIMESTAMP count is a hard absence.
- The side-exposure fit uses the 57 saved signed-open comparisons and their BatchExecutor call trees: increments are differences of two committed comparisons in one transaction, so the unknown stored base cancels, and each increment is paired with the midpoint the same transaction read.
- Every Foundry case restores the saved mixed-close prestate at block 48,901,631 and overrides only the implementation pointer, the instrument record and the market field word; accounting stays at its prestate value, so payout and queue columns are local scenario values, not current chain values.
- The set-2 variant uses the captured set-2 implementation, library and session-key manager; the live instrument record is byte-identical to the pinned one, and the pinned market field word is used so the pinned accounting stays consistent.
- No archive provider is configured, so no historical state read backs these rows; the missing observations above are the calls an archive endpoint would settle.
