## Vocabulary: the docs' numbering

The public docs at `docs.papertrade.xyz` call the code live between two implementation upgrades a **contract set**. Their protocol-changes page names contract set 1 (7 Oct to 21 Oct 2026, Exchange implementation `0x0f3febfc94876b0c895f7acecdc8f5c863b549ee`) and contract set 2 (live since 21 Oct 2026, Exchange implementation `0x0a44049dbbb6b4762a6ba37aa0f7548c0b4a3723`, upgrade transaction `0x4410b81e3eb76f83f5ddc4e3faee794fb67208d2f129bc013094b9d06055acb6`). That transaction is the newest multisig's `executeBatch` we decode above, so:

| This repo | Docs | Basis |
|---|---|---|
| `newest` | **contract set 1** (`/v1/`) | docs cite the exact pinned Exchange implementation address |
| `postpin_refresh` | **contract set 2** | docs cite the exact upgrade transaction hash and the BuilderRegistry address |
| `earlier_1`, `earlier_2` | undocumented | the docs' version picker stops at set 1 and calls it the initial production deployment; no page names either older address |

The `earlier_1` and `earlier_2` mapping is an inference from address and date: the docs never mention a pre-set-1 deployment, and I did not find an address list for one. Their /v1/ pages describe the pinned implementation's behaviour, not the two older sets', so a behavioural difference between an older set and /v1/ is not a documented change.

The public "Certificate" incident (PAPER described as a revenue-sharing certificate, transfers frozen, BBO-manipulation allegations) is reported as having paused *v1* parameters. On this repo's numbering v1 is `newest`, i.e. the pinned set, so the incident belongs to contract set 1 and predates the set 2 upgrade. **That is an inference from news reporting and the docs' version naming; neither the docs nor this repo state an incident cause for the 2026-10-21 upgrade, and the saved governance logs record no reason either.**

## Proven, current, unknown

**Proven from pinned saved evidence.** Three sets of 19 direct contracts exist in the recorded nonce order; every proxy's pinned implementation and admin are the saved pinned slot words; the two later Exchange variants match the manifest, and the three math-library addresses all hold the one 585-byte library runtime; no proxy ever emitted an `Upgraded` log and every implementation slot was equal at creation and at the pin.

**Proven from saved live and explorer evidence.** The 2026-10-20/21 deployer created seven named contracts whose runtimes reproduce their SHA-256 hashes; the newest multisig's records 9 and 10 hold the six-call batch that moved three proxies and wired the registry; the earlier-2 multisig's records 1299 and 1300 hold the same shape against earlier-2's own proxies; earlier set 1 was untouched. No proxy of any set emitted an `Upgraded` log after the pin and the newest ProxyAdmin emits only its own two owner events (both before the pin), which is why the upgrade is visible only in the slot words and the batch payloads.

**Read-only current.** Everything in the live tables comes from `latest` calls or explorer responses taken at the saved head; no live read is pinned state, and Core balances are public API values, not cryptographic proofs.

**Unknown.**

- twelve post-pin selectors have no hash-matched public name: four added Exchange, one added SessionKeyManager, three added Tokenomics, and two added plus two dropped Exchange-library entries
