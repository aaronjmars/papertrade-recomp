# PT-01 governed upgrade route at block 48,902,346

The newest Exchange proxy has a real upgrade control path: two current multisig signers can make its timelock call ProxyAdmin, which can replace the Exchange implementation. The [exact-runtime replay](../../scripts/atlas_pt01_governance_replay.py) runs all five pinned runtimes in one local EVM: multisig, timelock, ProxyAdmin, Exchange proxy, and original Exchange implementation. It seeds their pinned owner, signer, delay, transaction-count, and EIP-1967 slots, plus both PT-01 pending-sweep words. The target implementation is a local marker contract with no recovery logic.

| Tested path | Earliest simulated upgrade | Result |
|---|---|---|
| Schedule an Exchange upgrade with the pinned 604,800-second delay | 2026-10-25 21:02:21 UTC | One signer cannot schedule directly or self-confirm. Two signers schedule through the multisig; execution before the ready time fails; execution at the ready time changes the proxy implementation slot. |
| Execute the already scheduled delay change, then schedule an upgrade at 86,400 seconds | 2026-10-20 22:01:36 UTC | The saved delay-change operation becomes ready on 2026-10-19 22:01:36 UTC. Two signers can execute it through the multisig, reducing the delay to one day. A newly scheduled Exchange upgrade then succeeds at its one-day ready time. |

The second path uses the exact operation ID, predecessor, target, and ready timestamp in the [pinned timelock operation ledger](timelock_operations.json). Its predecessor had no scheduled operation at the pin; the deployed timelock's tested execution path does not require that predecessor to be done. The replay confirms this behavior through the complete owner chain. Both upgrade paths leave the two seeded pending words intact. An implementation whose full behavior is safe for this Exchange, its authorized installation, and any later HyperCore transfer are separate requirements. An [isolated cross-set replay](pt01_existing_replacement.md) tests the already deployed older replacement against these pending words but does not establish whole-implementation safety. The local marker proves upgrade authorization and proxy dispatch only.

This establishes a governed route to install a different implementation, not an existing recovery function or an actual recovery transaction. The dates are best-case simulated ready times from the pinned timestamp, assuming the required signer transactions are submitted immediately when eligible. The already scheduled delay change was pending at the pin; no execution was observed through that block. A one-day delay would affect only operations scheduled after the change. The test does not prove that any future implementation preserves Exchange storage layout or accounting invariants.
