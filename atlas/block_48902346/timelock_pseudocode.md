# Timelock reconstruction at block 48,902,346

Runtime: `0xb915fa41e824d6aa31bb833ee81220c0f2c8ea0f`, Solidity 0.8.24. This is a behavior reconstruction, not recovered source. [Machine evidence](timelock_behavior.json) is generated by `atlas_timelock_behavior.py` from pinned calls and read-only EVM traces.

## Storage

```text
slot 0: owner address
slot 1: minDelay seconds
slot 2: operationTimestamps mapping(bytes32 => uint256)
        0 = not scheduled, 1 = executed, value greater than 1 = scheduled ready timestamp
```

The owner at the pin is the one-of-two multisig. The minimum delay is 604,800 seconds. Getter opcode traces read slots 0 and 1, and the scheduled operation probes read and write `keccak256(abi.encode(operationId, uint256(2)))`.

## Core pseudocode

```text
hashOperation(target, value, data, predecessor):
    return keccak256(abi.encode(target, value, keccak256(data), predecessor))

hashOperationBatch(targets, values, data[], predecessor):
    dataHashes = [keccak256(item) for item in data]
    return keccak256(abi.encode(targets, values, dataHashes, predecessor))

owner(): return storage[0] as address
minDelay(): return storage[1]
operationTimestamps(id): return storage[keccak256(abi.encode(id, uint256(2)))]
isOperationDone(id): return operationTimestamps(id) == 1
isOperationPending(id): return operationTimestamps(id) > 1 and block.timestamp < operationTimestamps(id)
isOperationReady(id): return operationTimestamps(id) > 1 and block.timestamp >= operationTimestamps(id)

schedule(target, value, data, predecessor):
    require msg.sender == owner
    id = hashOperation(target, value, data, predecessor)
    require operationTimestamps[id] == 0
    ready = block.timestamp + minDelay
    operationTimestamps[id] = ready
    emit OperationScheduled(id, target, value, data, predecessor, ready)
    return id

execute(target, value, data, predecessor):
    require msg.sender == owner
    id = hashOperation(target, value, data, predecessor)
    require operationTimestamps[id] is scheduled and ready
    require msg.value == value
    operationTimestamps[id] = 1
    (success, result) = target.call{value: value}(data)
    require success
    emit OperationExecuted(id, target, value, data)
    return result

cancel(id):
    require msg.sender == owner
    require operationTimestamps[id] is scheduled and not done
    operationTimestamps[id] = 0
    emit OperationCancelled(id)

scheduleBatch(targets[], values[], data[], predecessor):
    require msg.sender == owner
    require arrays have equal, nonzero length
    id = hashOperationBatch(targets, values, data, predecessor)
    require operationTimestamps[id] == 0
    ready = block.timestamp + minDelay
    operationTimestamps[id] = ready
    emit BatchOperationScheduled(id, targets.length, predecessor, ready)
    return id

executeBatch(targets[], values[], data[], predecessor):
    require msg.sender == owner
    require arrays have equal, nonzero length
    id = hashOperationBatch(targets, values, data, predecessor)
    require operationTimestamps[id] is scheduled and ready
    require msg.value == sum(values)
    operationTimestamps[id] = 1
    for each target in array order:
        call target with corresponding value and data
        require success
    emit BatchOperationExecuted(id, targets.length)

updateMinDelay(newDelay):
    require msg.sender == address(this)
    minDelay = newDelay
    emit MinDelayUpdated(newDelay)

transferOwnership(newOwner):
    require msg.sender == address(this)
    require newOwner != address(0)
    owner = newOwner
    emit OwnerUpdated(newOwner)
```

Both batch methods reject empty or unequal array lengths with selector `0xff633a38` (public candidate `LengthMismatch()`). A one-target batch schedule wrote the expected ready timestamp. `BatchOperationScheduled(bytes32,uint256,bytes32,uint256)` reproduces its exact event topic, and the three data words match target count, predecessor, and ready timestamp. Executing that batch at its ready timestamp called the target and emitted `BatchOperationExecuted(bytes32,uint256)`. The operation timestamp was set to `1` before the external call in the opcode trace. In a two-target batch simulation, the first self-call succeeded and the second self-call reverted; the batch returned `0x15fcd675` and no storage change survived. A successful two-target batch emitted count `2` and left the second delay value in slot 1. With target values `1` and `2` wei, payment of `3` wei succeeded and the two targets received their respective amounts; payments of `2` or `4` wei reverted with `0xaa7feadc`. This supports ordered execution, exact total-value accounting, and atomic rollback for the tested cases.

## Observed paths and limits

- Both historical schedules were made by the multisig. Their IDs match the single-operation hash formula. Neither was executed on-chain through the pin.
- The first operation was ready at the pin. A read-only `execute` simulation from the owner succeeded and called Tokenomics. The second was pending, reverted with selector `0xf800799b` before its ready timestamp, and succeeded at that timestamp in a time-overridden simulation, calling the timelock itself to set the minimum delay to 86,400 seconds.
- Both operations name predecessor IDs whose timestamp was zero at the pin. Their successful simulations did not read the predecessors' mapping slots. The predecessor contributes to the operation ID, but these tested execution paths do not require the predecessor to be done.
- An outside caller was rejected by hash-checked `NotOwner()` (`0x30cd7471`) for schedule, execute, and cancel. Direct owner calls to `updateMinDelay` and `transferOwnership` were rejected by `0x29c3b7ee`; simulated self-calls succeeded. Transferring ownership to zero was rejected by `0x49e27cff`.
- A duplicate schedule was rejected by `0x9b382476`; canceling an unscheduled ID by `0x27c0d610`; canceling or executing a simulated done ID by `0x18d96a80`; and an execute call with one wei when the scheduled value was zero by `0xaa7feadc`. A failing target call was wrapped with `0x15fcd675`, and its earlier storage writes rolled back. Public error names are candidates until matched to source or reconstructed from all branches.
- The batch execute test used a hypothetical storage override and a time override. It proves behavior for that test state only. No batch operation was observed in historical timelock logs through the pin.
