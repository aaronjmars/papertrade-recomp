# Papertrade scoped audit findings

This workpaper covers the newest connected Papertrade suite at HyperEVM block 48,902,346. Findings below describe observed behavior at that pin. A [separate scope check](atlas/block_48902346/deployer_scope.md) found 38 older direct contracts and 38 older user deposit proxies with code, outside this behavior audit. PT-01 applies to the newest Exchange and its deposit proxies only. The findings do not rely on an assumed Papertrade source snapshot. PT-02 below applies to the implementation that is live now, after the contract-set-2 batch, and is recorded in the [live-code audit index](atlas/block_48902346/live2_audit.md) along with the rows this audit checked and cleared.

## PT-02: A paused market stores an unvalidated quote and cannot be unpaused, so every later close settles at the frozen price

**Status:** Confirmed in exact-runtime simulation, both implementations, guardian-gated. No market is paused on chain today (both market-pause words read zero at head 49,265,286), so this is latent rather than active. It is recorded as a finding because the trigger is a routine privileged action and the consequence has no on-chain remedy.

`pauseMarket` reads the raw HyperCore best bid and offer without the zero and crossed-book checks that the midpoint path applies, and it packs `flag | bid | ask | timestamp` into the market-pause word. The price helper's paused branch then returns `floor((bid + ask) / 2)` from that stored snapshot and never consults the oracle again. The named `unpauseMarket(uint32)` entrypoint reverts with `0xd9d193d3` in both the pinned and the live implementation, and a sweep of all 105 live dispatcher selectors from owner, guardian, keeper and unrelated callers across eight argument passes (3,255 calls, each in its own state snapshot) cleared the flag zero times. The positive control inside that sweep is `pauseMarket` itself, which does write the word from both owner and guardian, so the sweep is capable of detecting such a write. A static cross-check finds exactly one store into the mapping across each runtime, inside the `pauseMarket` body.

Consequence, measured: with a paused market and a crossed 300000/100000 book, both runtimes settle the next liquidation at 200000 while the live book reads 250700; with a zero book they settle at price 0. A paused market also rejects new opens with `MarketIsPaused()` (`0x741df939`) while closes and liquidations still settle at the snapshot, so the pause converts an instrument into close-only trading at a fixed price.

**Limits:** the downstream settlement cases are exact-runtime simulations with mocked HyperCore reads, not observed pausings; the sweep establishes absence of a clearing selector in the deployed dispatcher, not the absence of a differently shaped route, and governance itself can rewrite proxy storage through the ProxyAdmin. What would settle it: an archive trace of a liquidation executed while a market was paused.

## PT-01: Full-balance deposit sweeps failed on Core transfer gas and left two proxies uncredited

**Status:** Confirmed live instance of [Guardian KV-09](artifacts/guardian_papertrade_report.html), an accepted risk for inferred deposit settlement. HyperCore's public explorer identifies the immediate rejection of both spot sends. An exact-runtime replay also shows that the named owner reconciliation call rejects both pending sweeps. A narrow governed recovery candidate now has exact-runtime local tests and a prepared deployment plan, but the exact Core fee rule, Core acceptance for these two accounts, production upgrade safety, and actual recovery remain unverified. This is not a claim that an attacker can create an unfunded Exchange credit.

The Exchange asks each user's deposit proxy to convert its perp USDC to spot and send the full observed spot balance to the Exchange. The proxy queues both CoreWriter actions. Finalization credits the user's Exchange balance only after the proxy's normalized Core balance falls. In two observed cases, the perp-to-spot conversion executed, but the spot send failed with HyperCore's explorer error `Insufficient USDC balance for token transfer gas.` The public Core ledger shows no proxy-to-Exchange USDC send through the pinned block. Repeated successful EVM transactions cleared and re-requested the sweep without crediting the user.

The first and last sweep transactions are `0x99c1cfb96136fa735421048a9af350b2a54c85036723776276d4f9d85b570a20` and `0xeeb6dbb140d1ed4d435c169d99407ada8eb4a58dd554e9a071843246246f6b75` for the 50.050916 USDC case, and `0x47cd43341d3a3b5de575043f032b345814e822cc06c69c272fc99289a7f50032` and `0x28cac136ea4d5e29d413428616454c153f1a8ee6a8f120c45483b81830cfd98a` for the 12.1 USDC case.

The two last observed balances total **62.150916 USDC**. At the pin, both Exchange `pendingSweep` storage words still equal their last request events. No `Swept` event exists for either user from the first perp request through the pin, and a complete query for the owner reconciliation event returned zero logs. The proxy's current sweep path sends the full observed balance again on every retry. A simple top-up followed by that same path would increase the requested send amount, leaving no apparent reserve for transfer gas. A [different older Exchange replacement](atlas/block_48902346/older_sweep_retries.md) subtracted 1 USDC in two historical retries: both reduced sends executed with a 1 USDC Core fee and credited the older users, while the original full sends failed with the same gas error. One retry also included an external 1 USDC top-up. That replacement is installed behind another Exchange proxy and cannot alter the newest suite's pending requests as deployed. A [cross-set exact-runtime replay](atlas/block_48902346/pt01_existing_replacement.md) shows that installing it behind the newest Exchange proxy would queue 49.050916 and 11.1 USDC sends for these two pending states under mocked Core balances. Two counterfactual newest-suite transaction replays also match a signed-open batch and a mixed close, withdrawal, and staking batch under the replacement, including their logs and storage writes. Those samples do not prove overall upgrade safety or that HyperCore would execute the reduced sends. A separate exact-runtime test shows the older replacement still requests the full balance on a first sweep at the 10 USDC minimum, so its tested reserve does not cover that first-request path. A top-up of either affected newest proxy has not been tested. The pinned proxy runtime exposes an Exchange-only Core sweep and a user-only ERC-20 rescue call. The latter does not send HyperCore spot assets. Guardian's report describes `clearPendingSweep` plus `reconcileSweepCredit` as an owner recovery process. The pinned newest Exchange does not dispatch `clearPendingSweep(address)`, and `reconcileSweepCredit` reverts with hash-checked `SweepAlreadyPending()` for both saved pending words. A [separate earlier Exchange](atlas/block_48902346/older_exchange_clear.md) does dispatch that owner-only clear selector, but it cannot clear pending storage in the newest Exchange. A simulated direct storage clear lets owner reconciliation credit the user, but no deployed owner call that performs that clear has been identified. A credit alone would not move USDC out of either proxy. No reconciliation event was observed through the pin.

A [later status check](atlas/block_48902346/pt01_postpin_status.md) captured HyperEVM blocks 49,002,272, 49,050,036, and 49,063,456 on 2026-10-20. Both pending words and proxy runtime hashes still match the pin, the Exchange implementation slot still points to the same code, and complete post-pin archive queries found no sweep request, clear, or credit event for either user. The public Core info API returned no new non-funding ledger entries through the latest head and still reported 50.050916 and 12.1 USDC in the two proxy spot accounts shortly afterward. These later reads do not establish the transfer-gas rule, exclude a separate EVM credit, or prove the balances at an exact EVM head.

A [newest-suite fee control](atlas/block_48902346/pt01_newest_fee_controls.md) compares full public Core ledgers for 27 proxies with 73 credited perp sweeps against the two stalled proxies. All 27 controls have a 1 USDC fee recorded on their first returned inbound funding entry and a zero fee on their first outgoing USDC spot send; all 84 recorded sends to the Exchange have zero fee. Both stalled proxies have a zero fee on their first inbound entry and no successful outgoing send through the pin. A [combined 67-proxy cohort](atlas/block_48902346/pt01_funding_cohort.md) finds that the two stalled proxies and the two historically recovered older proxies were the only four with a zero-fee first returned funding entry. All four were first funded by the same sender in Core explorer `SystemSendAssetAction` transactions. The 63 other proxies first paid 1 USDC on funding and zero on their first outgoing spot send. This strengthens a first-use fee explanation without measuring a fee on either rejected send or proving the exact Core rule.

### Impact and limits

The evidence confirms that two deposit paths had pending, uncredited requests totaling 62.150916 USDC at the pinned block and that Core rejected their spot sends for insufficient USDC transfer gas. Two older, successfully recovered analogues each paid a 1 USDC fee. In a [38-proxy Core cohort](atlas/block_48902346/core_spot_fee_cohort.md), those were the only two charged among 112 older outgoing spot transfers, and one later transfer from the same sender had no fee. The [combined 67-proxy cohort](atlas/block_48902346/pt01_funding_cohort.md) isolates four zero-fee first funding entries from the same Core system sender: the two recovered older cases and the two newest stalled cases. All 63 other proxies first paid 1 USDC on funding and zero on their first outgoing send. This supports a first-use transfer-gas explanation but does not measure the fee on either rejected send or establish the exact Core validator rule. A governed route to install a different Exchange implementation is verified by the [full control-chain replay](atlas/block_48902346/pt01_governance_route.md). The already deployed older replacement requests reduced sends for both pending states, matches two sampled newest-suite trading transactions, and conditionally credits both users on next-block finalization in [local replays](atlas/block_48902346/pt01_existing_replacement.md). Its overall safety, Core acceptance, and actual USDC recovery remain unverified. The later status check shows the original Exchange implementation and no sweep-based recovery through block 49,064,506; the previously pending delay change is now executed and the timelock delay is one day, while other governance actions and later outcomes remain unverified. The replay rules out the common `clearPendingSweep(address)` signature and proves that the named reconciliation call requires pending storage to be cleared. It does not rule out a differently shaped privileged call or a Core-side remedy. The official [Hyperliquid activation fee documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/activation-gas-fee) describes a one-time fee for new accounts, but the saved evidence does not prove that this specific fee caused the rejection. An [RPC control](artifacts/audit_sweep_event_census/stalled_precompiles.json.gz) shows that the public HyperEVM endpoint returns later code and Core precompile values at block 1, so its apparent existing-user result cannot rule out a first-use fee at the historical request blocks. The archive RPC did not return usable historical precompile results. Public Core explorer and ledger responses are independent of the EVM traces but are API data, not cryptographic Core state proofs. The event census covers three known Exchange sweep topics; [32 of 53,125 spot-only credits](atlas/block_48902346/spot_settlement_stratified.md) now have individual Core delivery links, leaving 53,093 unpaired. The separate one-unit-decrease local replay remains a hypothetical overcredit concern, not a demonstrated exploit.

The actual recovery remains unproved for four specific reasons. The checked Core documentation does not give the predicate behind the explorer's transfer-gas error, and this audit did not identify a public API that dry-runs a CoreWriter send from either proxy. The candidate recovery upgrade and calls have not been executed on mainnet. The older replacement's compatibility is sampled rather than complete, including its older linked library, so it is not a validated production implementation for the newest Exchange. Finally, the next-block credit cases assume Core delivery and test zero or 1 USDC residual spot balance; neither delivery nor either residual state has been observed for these two users. No live governance action or CoreWriter send was submitted in this audit. The practical follow-up is to compare the cases with the team's accepted KV-09 monitoring and recovery runbook, independently review the narrow [candidate and exact production plan](recovery/README.md), and obtain the precise Core fee predicate or a safe live test before executing either reduced send. The candidate still needs broader trading and accounting compatibility checks and real Core delivery proof. The separate one-unit-decrease branch still needs a delivery-based test before it can be called an overcredit finding.

From a clean checkout with Python 3 and OpenSSL KECCAK-256 or Foundry `cast`:

```sh
python3 scripts/audit_sweep_event_census.py
python3 scripts/audit_perp_sweep_settlement.py
python3 scripts/audit_stalled_sweeps.py
python3 scripts/audit_stalled_precompiles.py
python3 scripts/atlas_older_sweep_retry_history.py

python3 scripts/atlas_pt01_newest_fee_controls.py
python3 scripts/atlas_pt01_funding_cohort.py

python3 scripts/audit_sweep_recovery_local.py
python3 scripts/atlas_pt01_governance_replay.py
python3 scripts/atlas_pt01_existing_replacement.py
python3 scripts/atlas_pt01_replacement_trade_compat.py
python3 scripts/atlas_pt01_replacement_mixed_compat.py
python3 scripts/atlas_pt01_replacement_getter_parity.py
python3 recovery/run_local.py
python3 -m recovery.preflight
python3 -m recovery.getter_parity
python3 -m recovery.plan
python3 scripts/atlas_verify.py
```

These commands verify saved evidence offline without a key. Set `PAPERTRADE_ARCHIVE_RPC` to an archive HyperEVM endpoint to refresh archive captures, including the getter comparison with `--capture`. The Core ledger and explorer captures use their public APIs. The local Forge scripts use `--run` to rebuild exact-runtime cases. No private RPC URL or credential is written to the artifacts.
