# PT-01 recovery candidate (redrive against the live Exchange set)

**Status: review only.** No contract has been deployed, no governance operation has been scheduled, and no CoreWriter action has been submitted by this work. The candidate was re-derived on 2026-10-22 against the Exchange implementation that is live now, `0x0a44049dbbb6b4762a6ba37aa0f7548c0b4a3723`, because the earlier candidate delegated ordinary calls to `0x0f3febfc94876b0c895f7acecdc8f5c863b549ee`, which the proxy no longer uses.

## Why the earlier candidate had to be re-derived

The 2026-10-20 governance batch replaced three proxy implementations. The Exchange proxy `0x6cd5661646289fb6e65ea5c032310fded797d0a2` now points at `0x0a44049dbbb6b4762a6ba37aa0f7548c0b4a3723`. The earlier candidate's `fallback()` and `receive()` delegated to the retired pinned implementation and its `_reconcile` called the retired implementation directly, so installing it as written would have silently dropped the live builder-fee, keeper, rebate and registry paths - including the six dispatcher entries the live set added. Everything else about the earlier design (the three owner-only recovery calls, the storage layout, the fee cases) carried over unchanged.

## Candidate behaviour

[`Pt01Recovery.sol`](Pt01Recovery.sol) is a temporary Exchange implementation for only the two PT-01 users. Every ordinary call delegates to the live implementation `0x0a44049d…`, its own three calls stay owner-only, and its fallback blocks the four live sweep-family selectors for the affected user while that user's recovery is active. Its three owner calls:

1. Queue a spot send of 49.050916 or 11.1 USDC, reserving 1 USDC in the affected proxy. It blocks the usual sweep and owner reconciliation entry points for that user while recovery is active.
2. If the first send succeeds without a fee and leaves 1 USDC, queue that residual as a second send.
3. After the proxy reaches zero spot USDC, clear its pending word and call the live owner reconciliation logic once. Credit is 49.050916 or 11.1 internal USD if a 1 USDC fee was paid, or the full 50.050916 or 12.1 if a zero-fee first send and residual send both deliver. Failure or a remaining Core balance prevents credit.

The code touches the observed `pendingSweep` mapping at slot 33, `lastSweepBlock` at slot 32, and one currently empty namespaced active-state slot; the test suite re-proves all three keys with `keccak256(abi.encode(user, 33))`, `keccak256(abi.encode(proxy, 32))` and `keccak256(abi.encode(user, 9))` against the live-derived slots. It checks the exact affected user and proxy addresses, the current raw Core balance, the pending amount and format, owner, block order, and the exact user, treasury, and total-balance credit deltas. The owner must independently confirm each Core execution and matching proxy and Exchange ledger entries before executing the next owner call. An EVM CoreWriter receipt alone proves only enqueue.

## Credit is conditional, unlike the live retry path

The live set-2 Exchange grew its own reduced-send retry: it reserves exactly one USD from the observed balance and queues that reduced amount, clearing the pending word when the reduced amount reaches zero (AuditIntents row **L2-D4-02**, `atlas/block_48902346/live2_intents.json`, evidence `artifacts/live2_intents/forge_observations.json`; the pinned retry instead kept the full balance and reverted below its 10 USDC minimum). Its `finalizeSweep` appears to credit the stored snapshot after the proxy balance falls, so a balance decrease without an equal Exchange receipt could create a shortfall (row **L2-D5-01**, status `plausible_unproven`). Two observed older reduced retries paid a separate 1 USD sender fee and credited exactly the delivered amount, so that fee alone is not evidence of overcredit; a real partial delivery or non-delivery balance decrease remains unobserved. This candidate does not inherit that: it credits only after the affected proxy's own Core balance reads **zero** - which a fee of any size other than the assumed one, or any partial delivery, would leave non-zero - and only when the pending word it wrote matches the credit exactly, so it can never credit more than the observed post-send state and the two public Core ledgers support. That makes it strictly more conservative than the live path, at the cost of needing the operator to confirm delivery before each finalize. The local suite exercises that: a residual balance blocks credit, and a changed Core balance rejects finalization.

## Execution order after review and approval

1. Recheck EVM implementation, owners, pending and active words, proxy runtimes, both public Core ledgers, both spot balances, current timelock delay, signer set, candidate address, and operation slots. Stop if any expected value has changed.
2. Deploy the exact [`compiled.json`](compiled.json) init code through the checked CREATE2 factory. Check the deployed address and runtime hash. Have the multisig schedule the necessary timelock operations. Each can execute only after the live minimum delay. The saved [production plan](production_plan_20261022.json) contains the exact target, value, data, operation ID, and submit payload for each action.
3. Upgrade the Exchange to the candidate. Run ordinary path smoke checks, then enqueue the smaller 12.1 USDC case first. Wait for the Core execution record and matching transfers in both public ledgers. If the send is rejected, do not finalize or move to the larger case.
4. If the smaller proxy has zero USDC after a 1 USDC fee, finalize 11.1. If it has 1 USDC after a zero-fee send, queue the residual, verify its separate delivery, then finalize 12.1. Any other balance or missing ledger match stops the sequence. Repeat the same sequence for the 50.050916 USDC case.
5. Verify each user's internal balance, Exchange treasury and total balances, pending and active words, Core proxy and Exchange balances, exact fee entries, and lack of duplicate credits. Restore the **live** implementation `0x0a44049d…` after both recoveries are verified, then verify the restored implementation slot and ordinary paths again.

The plan needs **two of the three multisig signers** (`0xaa7577a7a7a27aa7fcf6d0ec481b87df3ad0f6a88e`, `0xe9686c8e11d80c8d78736485fcb6b6d7f4d7692e`, `0x9028f3b5b6b0d69e4e84ff555ade17114c3d1e72`) to submit and confirm each timelock operation, and the timelock's live minimum delay is one day, so the earliest possible execution is one day after the first schedule.

## Failure states

| Observed outcome | Candidate state | Required next step |
| --- | --- | --- |
| The EVM CoreWriter call reverts | The whole enqueue transaction reverts; pending and active storage stay unchanged | Diagnose the EVM failure before retrying. |
| The EVM enqueue succeeds but Core later rejects the first reduced send | Recovery stays active, pending records the reduced amount, and the proxy still holds its original USDC | Stop. The candidate has no abort or reset call. Restoring the live implementation without a reviewed state repair could use a mismatched pending amount. |
| The first send delivers without a fee, but Core rejects the 1 USDC residual send | The first amount is in the Exchange Core account, 1 USDC remains in the proxy, and no internal credit has been issued | Stop. The candidate has no partial-credit or residual-repair call. Independently verify both Core ledgers and design a separate exactly-once repair. |
| A Core ledger, balance, or EVM storage value differs from the expected outcome | The candidate cannot establish exact delivery and credit from its own checks | Stop before finalization or the larger case. Reconstruct the state with the team runbook. |
| The live dispatcher gains a new sweep-family selector mid-flight | The fallback would no longer block that route for an affected user | Re-run `python3 -m recovery.live_facts` and compare the added-selector list before any owner call. |
| Someone reaches the live dust branch before the recovery starts | A cleared pending word no longer equals the affected balance, so `rescueEnqueue` refuses to act | Stop, re-read the live pending word and the sweep-family log range, and decide whether to re-request the sweep before scheduling anything. The two balances (50.050916 and 12.1 USDC) are far above the dust threshold, and the preflight shows no sweep-family event for either user since the pin. |

An EVM enqueue receipt is not a Core delivery receipt. The operator must match the Core execution and both account ledgers before any next governance call. The saved plan has no abort, reset, or partial-credit operation.

## Open gates

The exact Core predicate behind `Insufficient USDC balance for token transfer gas.` is still undocumented in the checked [activation fee guidance](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/activation-gas-fee). Two older real retries succeeded with a 1 USDC reserve, but that does not prove acceptance for these two proxies. There is no identified public dry-run API for a CoreWriter send from either proxy. Local CoreWriter and balance responses are mocked. This candidate has not had an independent production security review or a complete trading and accounting path comparison; the added delegatecall also changes gas use for ordinary calls, and the live set's six new selectors change the ordinary path mix relative to the pinned comparison. The two historical replays are anchors for the pinned implementation only: the live set still reproduces the signed-open path exactly but emits seven fewer logs on the sampled mixed path, so the live set's own behaviour on paths this workstream never replayed is not compared to anything here. Papertrade's accepted KV-09 monitoring and incident runbook have not been obtained. The archived trade and mixed replays are samples, not complete path coverage, and the two historical replays do not cover any of the six newly added live selectors.

No live write is authorized by this document. Deployment, governance scheduling, upgrading, CoreWriter sends, and finalization require explicit maintainer approval and the Papertrade governance signers.
